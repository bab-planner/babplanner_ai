# 밥플래너 AI 연구 트랙

서비스 코드(`src/babplanner_ai/`)는 계약과 경계다. 여기는 그 계약 뒤에 들어갈
모델을 만드는 곳이다. 둘을 나눠 둔 이유는, 연구가 진행 중이라는 사실이
서비스의 동작을 바꾸면 안 되기 때문이다. 이 폴더 전체를 지워도 FastAPI
서비스는 그대로 뜬다.

## 세 가지 문제

| | 이름 | 입력 | 출력 | 상태 |
|---|---|---|---|---|
| AI-1 | [CCTV 기반 비식별 혼잡도·이용 인원 분석](cctv_counting/) | 영상 | 현재 인원, 입장 인원 | baseline 구현됨, 벤치마크 미측정 |
| (보관) | [식판 이미지 기반 잔반 분석](waste_estimation/) | 이미지 | 잔반률, 신뢰도 | **서비스 범위 밖.** 과거 연구 기록. 운영 경로 없음(잔반 인증은 Backend의 관리자 승인) |
| AI-3 | [과거 이용 패턴 기반 식수 예측](demand_forecasting/) | 시계열 | 예상 식수 | 합성데이터 PoC 파이프라인. 실제 데이터 없음 |

최종 AI 서비스 범위는 CCTV 혼잡도(AI-1)와 식수 예측(AI-3) 둘이다. 잔반 분석과 발주 추천은
서비스에 없고, 이 폴더의 잔반 연구는 오프라인 기록으로만 남아 있다.

## 공통 문제

셋은 입력도 출력도 다르지만 같은 벽에 부딪힌다.

> **실제 단체급식 환경에서 AI 입력 데이터는 완벽하지 않고, 환경은 계속
> 변한다.**

무엇이 불완전한지는 문제마다 다르다.

**AI-1 (CCTV).**
카메라 각도가 현장마다 다르다. 점심때는 밝고 저녁때는 어둡다. 배식 줄에서
사람이 서로를 가린다. 붐빌수록 상자가 겹쳐 적게 세인다. 그런데 하필 붐빌
때의 숫자가 가장 필요하다.

**AI-2 (잔반).**
찍는 각도가 매번 다르다. 조명이 다르다. 식판 구성이 학교마다 다르다. 그리고
결정적으로, **먹기 전 사진이 없다.** 남은 양은 보이는데 원래 얼마였는지는
안 보인다. 같은 양이 남아도 많이 받았으면 적게 남긴 것이다.

**AI-3 (식수 예측).**
새 급식소는 과거가 없다. 학기가 시작하면 패턴이 바뀐다. 요일마다 다르고
시험 기간에 또 다르다. 그리고 지금 이 저장소에는 실제 식수의 정답이 쌓이는
곳 자체가 없다(루트 README의 "수요 예측: 정답 데이터가 없다" 참고).

## 공통 목표

> **불완전한 현장 데이터에서, 신뢰할 수 있는 예측만 서비스로 내보낸다.**

"신뢰할 수 있는 것만"이 핵심이다. 세 문제 모두 정답률 100%가 불가능하고,
틀린 값을 자신 있게 내보내는 것이 값을 안 내보내는 것보다 나쁘다.

- 잔반 분석이 흐릿한 사진에 대해 아무 숫자나 내면, 그 숫자로 포인트가 나간다.
- 혼잡도가 역광 프레임에서 3명이라고 하면, 앱은 한산하다고 표시한다.
- 식수 예측이 근거 없이 400명이라고 하면, 그만큼 식자재를 산다.

그래서 세 모듈 모두 값과 함께 **그 값을 얼마나 믿을 수 있는지**를 같이 낸다.
AI-1은 `reliability_flag`, AI-2는 APPROVE/REJECT, AI-3는 예측 구간이다. 형태는
다르지만 목적은 같다.

## 연구 흐름

세 트랙 모두 같은 순서로 간다. 지금 AI-1이 1~2번 사이에 있다.

```
1. Baseline                    공개 pretrained 모델로 일단 끝까지 돌린다
2. Public Dataset Evaluation   정답이 있는 공개 데이터에서 정량 평가
3. Domain Shift Analysis       현장과 비슷한 조건에서 얼마나 나빠지는가
4. Failure Case Analysis       어디서 어떻게 틀리는가
5. Reliability / Confidence    틀릴 때를 미리 알 수 있는가
6. Service Integration         믿을 수 있는 것만 백엔드로
```

**1번을 건너뛰지 않는다.** 처음부터 큰 모델을 학습하면, 나중에 성능이 나와도
그것이 모델 덕인지 문제가 원래 쉬웠던 것인지 알 수 없다. 먼저 단순한 것으로
바닥을 재고, 그 위에서 개선을 주장한다.

**복잡하게 만드는 것 자체를 목표로 두지 않는다.** detection-only가 충분한데
추적을 얹는 것은 개선이 아니라 비용이다. AI-1에서 두 baseline을 같은 설정으로
나란히 돌릴 수 있게 만든 이유가 이것이다.

## 지키는 것

**성능 숫자를 만들어내지 않는다.** 정답 데이터로 재지 않은 값은 "미측정"이라고
적는다. 보고서의 빈칸이 지어낸 숫자보다 낫다.

**합성 데이터를 현장 데이터라고 부르지 않는다.** 지금 저장소에 있는 것은
전부 합성 fixture다. 실제 급식소 데이터는 아직 하나도 없다.

**공개 데이터는 출처와 라이선스를 확인하고 쓴다.** 그리고 **코드 라이선스,
가중치 조건, 학습 데이터 조건은 서로 다른 문서다.** 하나가 허용적이라고
나머지가 따라오지 않는다. 확인하지 못한 것은 UNVERIFIED로 적고 추측으로
확정하지 않는다. 비상업 라이선스 데이터로 낸 숫자는 상용 서비스의 근거가 될
수 없다.

**남의 알고리즘 이름을 자기 구현에 붙이지 않는다.** 아이디어를 빌린 것과
구현을 재현한 것은 다르다. 이름이 사실과 어긋나면 나중에 나온 숫자가 원
논문의 성능으로 읽힌다.

**개인을 식별하지 않는다.** AI-1은 얼굴을 다루지 않고, 사람을 영상 밖에서
다시 알아보지 않으며, 회원 정보와 연결하지 않는다. 자세한 것은
[cctv_counting/README.md](cctv_counting/README.md)의 개인정보 절.

**원본 영상, 모델 weight, 대용량 데이터셋은 커밋하지 않는다.** `.gitignore`에
있고, 커밋 전에 `git status`로 확인한다.

## 폴더

```
research/
  cctv_counting/        AI-1. 이번 단계의 작업 대상
    configs/            실험 설정 (YAML)
    datasets/           공개 데이터 후보 조사, 정답 파일 템플릿
    evaluation/         평가 절차
    experiments/        실행 결과가 쌓이는 곳 (git 제외)
    scripts/            실행 진입점
    src/cctv_counting/  라이브러리
    tests/              단위 테스트
  waste_estimation/     AI-2. README만
  demand_forecasting/   AI-3. 합성데이터 PoC (생성 → EDA → 학습 → 예측 CLI)
```

`reports/`는 저장소 루트에 있다. 포트폴리오용 보고서가 들어간다.

## 테스트

연구 트랙 테스트는 서비스 테스트와 같은 명령으로 돈다.

    .venv\Scripts\python.exe -m pytest

연구 코드의 핵심 로직은 torch도 opencv도 없이 도는 것을 원칙으로 한다.
무거운 의존성이 있어야만 검증되는 로직은, 실제로는 아무도 검증하지 않게 된다.

## 환경

`.venv`는 **FastAPI 서비스 개발 환경**이다. 연구용 무거운 의존성
(torch/CUDA, 수 GB)을 여기에 넣지 않는 것을 권장한다. 서비스가 깨졌을 때
원인이 연구 쪽인지 서비스 쪽인지 가릴 수 있어야 한다.

실제 영상 추론이 필요해지면 별도 환경을 만든다.

    py -3.12 -m venv .venv-cctv
    .venv-cctv\Scripts\python.exe -m pip install -e ".[cctv]"

`.venv-cctv/`는 `.gitignore`에 있다.
