# AI-3. 과거 이용 패턴 기반 예상 식수 예측

*Data-efficient Meal Demand Forecasting under Limited Historical Data*

> **이 폴더에는 모델 코드가 없다.** 이번 단계에서 만들지 않았다. 여기 있는
> 것은 무엇을 만들 것인지에 대한 정의다.

## 목표

특정 급식소의 특정 끼니에 몇 명이 올지 예측한다. 그 결과가 발주 추천으로
이어진다(`src/babplanner_ai/procurement/`).

## 핵심 연구 질문

> **신규 급식소에서, 며칠 정도의 과거 데이터가 있어야 쓸 만한 식수 예측이
> 가능한가?**

이것이 이 트랙을 다른 시계열 예측과 구분하는 지점이다. 보통의 수요 예측은
몇 년치 데이터를 가정한다. 급식소는 그렇지 않다.

- 새 학교가 들어오면 과거가 0일이다
- 학기가 시작하면 패턴이 바뀐다
- 요일마다 다르고, 시험 기간에 또 다르다
- 방학이 있다

그래서 "데이터가 많으면 잘 맞힌다"는 답은 쓸모가 없다. **얼마나 적은 데이터로
얼마나 맞힐 수 있는가**, 그리고 **데이터가 부족할 때 그 사실을 아는가**가
문제다.

## 그 전에: 정답 데이터가 없다

이건 모델을 아직 안 만들었다는 것과 다른 문제다. 루트 README에 이미 적혀 있다.

예측이 맞히려는 값은 **실제 급식 이용 인원**이다. 그런데 지금 시스템 어디에도
그 값이 정답으로 쌓이는 곳이 없다.

- `congestion_observations.peopleCount`는 특정 시점의 혼잡도 관측이다. 한 끼를
  실제로 먹은 사람 수가 아니다. 이 값을 정답으로 쓰면 관측 시각과 관측 방식에
  따라 정답이 흔들린다.
- 잔반 제출 건수는 인증에 참여한 사람 수다. 이용자 전체가 아니다.
- 식권/입장 기록 같은 canonical source가 아직 없다.

**실제 식수 ground truth source가 생기기 전까지 이 트랙의 학습은 불가능하다.**

### AI-1이 여기에 닿는 지점

CCTV의 **entry counting**이 그 대리 지표 후보다. 입구를 IN 방향으로 넘은
사람 수는 한 끼 이용 인원에 가깝다. 혼잡도 관측(순간값)보다 훨씬 가깝다.

다만 그것이 실제 식수와 얼마나 맞는지는 검증되지 않았다. 검증 전에 정답으로
쓰면, 모델은 카메라의 계수 오차를 학습한다. AI-1의 entry count 정확도를 재는
것이 이 트랙의 선행 조건이다.

이것이 AI-1에서 occupancy와 entry count를 굳이 분리한 이유이기도 하다. 하나로
합쳤으면 여기서 쓸 수 있는 값이 없었다.

## Baseline 계단

**단순한 것부터 올라간다.** 각 단계는 바로 아래 단계를 이겨야 의미가 있다.

```
1. 전날과 같다                     가장 단순. 이걸 못 이기면 아무것도 아니다
2. 지난주 같은 요일과 같다          요일 효과만 반영
3. 최근 N일 이동평균                노이즈 평활
4. 같은 요일 이동평균               2 + 3
5. 선형 회귀 / 트리 모델            요일, 메뉴, 날씨, 학사일정 특징
6. 시계열 모델                      계절성과 추세를 명시적으로
```

**1~4를 건너뛰지 않는다.** 이런 문제에서 "지난주 같은 요일"은 놀랄 만큼 강하다.
복잡한 모델이 그것을 못 이기는 경우가 흔하고, 비교 대상이 없으면 그 사실을
알 수가 없다. 그리고 데이터가 적을 때는 단순한 쪽이 실제로 더 낫다. 그것이
이 트랙의 연구 질문 자체이기도 하다.

## 평가

**시간을 지켜 나눈다.** 무작위 분할을 쓰지 않는다. 미래 데이터로 과거를 예측하는
것은 실제로 할 수 없는 일이고, 그렇게 재면 성능이 실제보다 좋게 나온다.
과거 → 미래 순으로 자른다.

**데이터 양을 축으로 삼는다.** 이 트랙의 핵심 질문에 답하려면 결과가 이런
모양이어야 한다.

| 과거 데이터 | 7일 | 14일 | 30일 | 60일 | 90일 |
|---|---|---|---|---|---|
| baseline 1 (전날) | | | | | |
| baseline 4 (요일 이동평균) | | | | | |
| 모델 | | | | | |

**"며칠부터 모델이 baseline을 이기는가"** 가 답이다.

**cold-start를 따로 본다.** 과거 0일인 신규 급식소는 위 표에 들어가지 않는다.
그때 무엇을 낼 것인가는 별도 문제다. 비슷한 규모의 다른 급식소 평균을 쓸
것인지, 아예 예측하지 않을 것인지.

**지표.** MAE(단위가 사람 수 그대로) + bias. 과대 예측은 음식이 남고, 과소
예측은 사람이 못 먹는다. **비용이 비대칭이므로 부호를 반드시 본다.**
MAPE는 주 지표로 쓰지 않는다.

**예측 구간을 낸다.** "380명"보다 "350~410명"이 발주에 쓸모 있다. 이것이 이
트랙의 신뢰 신호다. AI-1의 `reliability_flag`, AI-2의 APPROVE/REJECT와 같은
자리에 있다.

## 이미 정해진 것

`src/babplanner_ai/demand/`에 API와 `DemandEstimator` 경계가 있다. 지금은
fixture이고 기본 모드는 `disabled`다.

`AIDemandRequest`는 과거 관측치 배열을 받지 않는다. 어느 기간의 무엇을 집계한
값인지 정의된 적이 없는 배열을 계약에 두면, 보내는 쪽은 모델이 그것을 쓰고
있다고 믿고 받는 쪽은 무시하게 된다. **feature 계약 확장은 ground truth source가
정해진 뒤 별도 버전에서 한다.**
